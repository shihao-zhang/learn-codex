## Context

当前仓库已经完成 Step 2 初版：12 章都有 README、Mermaid 图、Python 教学 mock、真实映射、生产差异、练习和事实核验清单。现有约束是清楚的：本仓非官方，研究边界是 `openai/codex` 的公开 Rust CLI harness；Python mock 只用于教学，不代表官方实现。

当前短板也很明确：多数“已核实官方事实”仍以固定 SHA 的目录/文件锚点为主，章节机制解释还缺少机制点级证据。Phase 3~4 要把仓库从“学习地图 + 教学 mock”推进到“可追溯源码导读”，并优先解决 s08~s11 的待核实区域。

## Goals / Non-Goals

**Goals:**

- 建立机制点级证据登记：每条关键解释都能追到固定 SHA permalink、核验状态、核验日期和未决问题。
- 为 `已核实官方事实` 的升级建立清晰门槛，避免“路径存在”被误读成“行为已核实”。
- 优先核验 s08~s11 的真实边界，决定哪些内容可升级、哪些必须继续保持待核实。
- 强化 `scripts/check_docs.py` 和测试，防止未登记链接、错误 SHA、无证据断言和状态标签漂移。
- 保持读者体验：面向 AI 产品经理仍然先讲清机制意义，面向平台设计者提供源码追踪路径。

**Non-Goals:**

- 不调用 OpenAI API，不引入真实模型执行，不把 mock 变成 Codex 复刻实现。
- 不覆盖 Codex Cloud、IDE 私有能力、未公开内部服务或泄漏材料。
- 不追求一次性核实全部字段和全部 Rust 调用链；优先处理章节主机制和待核实高风险区。
- 不改变仓库许可证、非官方声明和当前 12 章主线结构。

## Decisions

1. 采用“统一 source-evidence 索引 + 全局 fact snapshot”的双层证据模型。

   - `docs/source-evidence.md` 作为唯一机制级证据索引，避免每章 sources 文件漂移。
   - `docs/fact-snapshot.md` 继续作为全局目标 commit、release、易过期点和官方锚点索引。
   - 每章 README 只保留真实映射和指向统一证据索引的链接，降低维护成本。
   - 备选方案是每章维护独立 `sources.md`；缺点是检查脚本需要跨文件聚合，状态漂移风险更高。

2. 证据颗粒度使用“机制点”而不是“每句话”。

   - 每个机制点绑定一个或多个 fixed-SHA permalink，并说明核验范围。
   - 对产品解释、教学比喻、练习题不强制绑定源码，但不能声称为官方事实。
   - 备选方案是逐句标注；精度更高，但维护成本过重，容易牺牲可读性。

3. s08~s11 保持保守升级策略。

   - 只有当章节主机制、入口路径、关键类型/函数和行为边界都核实后，才允许从 `待核实` 升级。
   - 如果只确认路径存在或发现能力不是 CLI 主线，就继续保持 `待核实`，并在 README 中说明原因。
   - 备选方案是先写完整解释再补证据；风险是把推断沉淀成事实。

4. 检查器只验证可机械判断的合同。

   - `check_docs.py` 负责固定 SHA、状态映射、证据登记、占位残留、待核实声明等机器可判定规则。
   - 语义正确性仍靠人工/Claude review 和源码核验记录，不能假装脚本能证明官方等价。

## Risks / Trade-offs

- [Risk] 行号 permalink 会随上游源码更新而过期或变得难维护 → 使用固定 commit；更新快照时集中迁移，并保留核验日期。
- [Risk] 证据表过密会降低 PM 读者的可读性 → README 主体保持解释性，证据表集中放入 `docs/source-evidence.md`。
- [Risk] s08~s11 核验后发现部分能力不属于开源 CLI 主线 → 明确降级为旁支/待核实，不为了章节完整性强行升级。
- [Risk] 检查器规则过严导致贡献门槛变高 → 先覆盖关键回退风险，再逐步增加规则；报错信息必须直接指出修复方式。
- [Risk] 教学 mock 升级时被误解为官方实现 → mock 输出、README 和 tests 继续保留非官方/教学免责声明。
