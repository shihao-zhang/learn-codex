# s02_protocol_events

## 状态标签

状态：已核实官方事实

## 本章回答什么

本章回答：agent 运行时如何把内部动作变成客户端能理解的产品状态。

在 agent 系统里，事件协议不是“把日志打印出去”。它承担三层职责：

- 把用户输入、模型输出、工具调用、错误和完成状态整理成稳定结构。
- 让 CLI、App Server 或其他客户端知道当前 turn 到了哪一步。
- 为恢复、调试、审计和兼容性留下可追踪的状态边界。

## 对产品与平台设计的意义

对 AI 产品经理来说，事件协议决定用户看到的“正在思考”“正在运行命令”“等待授权”“已完成”“失败原因”。如果事件太粗，用户只能看到一个长时间 spinner；如果事件太细但没有语义，用户会被噪声淹没。

对平台设计者来说，protocol 是运行时和界面之间的契约。它需要稳定、可版本化、可恢复，并能承载流式输出、工具状态、错误码和权限请求。核心权衡是：协议越稳定，演进越慢；协议越贴近内部实现，客户端越容易被内部重构牵连。

## PM 真正关心的问题

- 用户看到的状态是否能解释等待原因？“正在处理”不够，产品需要区分模型输出、工具执行、权限等待、失败和完成。
- 失败能不能被恢复和追责？没有稳定错误事件和关联信息，客服、开发者和用户只能靠截图猜测发生了什么。
- 客户端升级不一致时会怎样？协议新增事件或字段时，旧客户端应该能降级显示，而不是把未知状态误判成成功或崩溃。

## 核心机制

- `protocol event` 是客户端可见的状态变化。它应该回答“发生了什么、属于哪个 turn、是否终止、是否需要用户动作”。
- `input/output item` 是模型和运行时之间传递内容的结构化单元。它可能代表用户输入、模型消息、工具请求、工具结果或错误，而不是纯文本拼接。
- `trace` 用来把一次模型步骤、一次工具调用、一次错误或一次权限请求串起来。没有关联 ID，调试长任务会很快变成猜谜。
- 事件协议要区分“流式内容”和“状态事件”。流式文本可以频繁到达，但状态事件必须能驱动 UI 状态机。
- schema drift 是长期风险：一旦字段改名、枚举新增、语义变化，旧客户端可能误判状态。所以新增事件要考虑兼容默认值、未知字段处理和降级显示。
- 好的协议不会把所有内部细节都暴露给客户端。它选择性暴露产品需要的事实，同时保留内部重构空间。

## 典型 failure path

教学 failure path：客户端或运行时交给协议层的 tool output 结构不符合 schema。理想处理不是把错误吞掉，也不是让 UI 继续显示长 spinner，而是发出稳定、可归因的错误状态，让客户端知道这次 turn 已经不可继续或需要重试。

这个例子服务于产品判断：协议错误、工具业务失败、模型内容不满意是三类不同问题。它不声明官方 Codex 对未知字段一定采用同样校验策略或错误码；真实事件类型、item 类型和字段命名仍以固定 SHA 的 `protocol/src` 为准。

## 教学简化与生产差异

- mock 把事件压缩成 `request -> event -> event -> completed`，真实实现会包含更多类型、更多字段、流式增量、错误结构、权限相关事件和客户端状态同步。
- 教学图把 transport 画成单线，生产里可能有 CLI 进程内消费、app-server transport、持久化恢复、测试 harness 等不同路径。
- 教学里把 trace 画成简单关联线；生产里 trace 还会服务 telemetry、debug、审计和故障复盘。
- 教学内容只说明协议设计语义，不声明 Python mock 的事件名、字段名或顺序是官方实现。

## 练习

1. 运行 mock，给每个事件标注它服务的是 UI 展示、运行时恢复、错误处理还是调试追踪。
2. 设计一个“等待用户授权”的事件：至少包含 turn 标识、请求原因、可选决策和是否阻塞后续执行。
3. 假设新增一个工具状态事件，写出旧客户端不知道这个事件时的降级策略。
4. 对比“日志”和“事件”：同样是 shell 执行失败，哪些信息应该进入用户可见事件，哪些只适合进入调试 trace？
